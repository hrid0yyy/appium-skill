# Appium skill passes audit, needs eleven fixes

The skill's API layer has no errors. Every capability, Options property, `mobile:`/`windows:` extension name, argument and default it gives was checked against the installed packages (Appium 2.19.0, uiautomator2@4.2.9, windows@4.4.7, Appium-Python-Client 6.1.5). Real `webdriver.Remote` sessions built from the skill's patterns reached the driver layer on both platforms. No server-version gating or BiDi default gets in the way. So an agent with no web access will write correct Appium calls. The problems are around the edges. **One confirmed template bug** makes every failing test in a file overwrite the same screenshot. **The Calculator sample breaks** whenever Calculator was last left in a non-Standard mode. **The PowerShell form of the `--allow-insecure` command** probably turns the insecure features off without any error. **Four error strings in troubleshooting.md are not the text Appium actually prints**, so an agent searching logs for them finds nothing. **Several setup statements are out of date or wrong**: Node 20 is now end of life, `winget install OpenJS.NodeJS.LTS` now installs untested Node 26, `appium driver update` behaves differently than described, and Command-line Tools is missing from the SDK list. None of these stops a careful agent completely, but each one costs a debugging loop. All fixes are listed below with current text, corrected text and evidence. Paths are relative to `/home/user/appium-skill/.claude/skills/appium-android-windows/`.

## The core API surface is verified line by line

The router rules and the minimal session shapes in SKILL.md are correct for client 6.1.5 talking to server 2.19. `UiAutomator2Options().to_w3c()` and `WindowsOptions().to_w3c()` produce correctly prefixed W3C payloads (`appium:` everywhere, plus `ms:waitForAppLaunch`). `GET /status` on a live 2.19 server returned `"version":"2.19.0"`, and `GET /wd/hub/status` returned 404. That confirms the skill's rule to leave out the base path. A client session against that server matched "AndroidUiautomator2Driver (v4.2.9)" and failed only on missing `ANDROID_HOME` and on "WinAppDriver tests only run on Windows", which is expected on a Linux sandbox. The PyPI pins are current: **Appium-Python-Client 6.1.5 requires `selenium<5.0,>=4.51.0`, and pytest 9.2.0 and python-dotenv 1.2.4 are the latest versions** ([PyPI](https://pypi.org/pypi/Appium-Python-Client/json), [pytest](https://pypi.org/pypi/pytest/json), [python-dotenv](https://pypi.org/pypi/python-dotenv/json)). The version pinning is also justified. **4.2.9 is the last uiautomator2 4.x and 4.4.7 is the last windows 4.x**. Newer majors declare peer `appium ^3.0.0-rc.2` or `^4.0.0-beta.6` ([npm uiautomator2](https://registry.npmjs.org/appium-uiautomator2-driver), [npm windows](https://registry.npmjs.org/appium-windows-driver), [npm appium](https://registry.npmjs.org/appium)).

For Android, every Options property the skill names exists in 6.1.5. The ones it routes through `set_capability` (`forceAppLaunch`, `hideKeyboard`, `autoLaunch`) correctly have no typed property. Every `mobile:` name and argument matches `execute-method-map.js` in the installed driver. The documented defaults match the driver README: avd timeouts 60000 ms, systemPort 8200–8299, newCommandTimeout 60 s, `query_app_state` 4 = foreground. The `mobile: scroll` return-value and container semantics are confirmed by the driver's own gestures doc ([android-mobile-gestures.md v4.2.9](https://raw.githubusercontent.com/appium/appium-uiautomator2-driver/v4.2.9/docs/android-mobile-gestures.md)). The ApiDemos page object is right as well. The APK's `SimpleAdapterWithDesc` sets every list row's content-desc to its text, and "WebView" is row 39 of 42 under Views, so the scroll is required and the exact-match accessibility id works. The permission-dialog ids `com.android.permissioncontroller:id/permission_allow_button` / `_foreground_only_button` / `_one_time_button` exist in current AOSP and are hard-coded in Google's CTS ([grant_permissions.xml](https://raw.githubusercontent.com/LineageOS/android_packages_modules_Permission/lineage-22.2/PermissionController/res/layout/grant_permissions.xml), [BaseUsePermissionTest.kt](https://raw.githubusercontent.com/LineageOS/android_packages_modules_Permission/lineage-22.2/tests/cts/permissionui/src/android/permissionui/cts/BaseUsePermissionTest.kt)).

For Windows, every Calculator AutomationId the template uses exists in Microsoft's XAML, and the display Name format is `Display is %1` ([NumberPad.xaml](https://raw.githubusercontent.com/microsoft/calculator/main/src/Calculator/Views/NumberPad.xaml), [CalculatorStandardOperators.xaml](https://raw.githubusercontent.com/microsoft/calculator/main/src/Calculator/Views/CalculatorStandardOperators.xaml), [Resources.resw](https://raw.githubusercontent.com/microsoft/calculator/main/src/Calculator/Resources/en-US/Resources.resw)). The WindowsOptions properties, their units (createSessionTimeout in ms, `ms:waitForAppLaunch` in seconds), the `windows:` extension table, the prerun/postrun semantics, the WAD port range 4724–4824 and the multi-window guidance all match the driver source and Microsoft's WAD FAQ and tests ([FAQ.md](https://raw.githubusercontent.com/microsoft/WinAppDriver/master/Docs/FAQ.md), [Window.cs](https://raw.githubusercontent.com/microsoft/WinAppDriver/master/Tests/WebDriverAPI/Window.cs)).

B3 needs one companion warning, which belongs in the severity-two group but is easiest to apply alongside it. **The prefix must be the lowercase driver extension name** (`uiautomator2`, `windows`). Calling the real `configureDriverFeatures` showed that `UiAutomator2:adb_shell` leaves `allowInsecure=[]`, **with no error**. The reason is that the umbrella server compares the prefix case-sensitively against the extensions.yaml key. Appium's own guide says the prefix is the "automationName", which steers agents toward the CamelCase spelling that fails ([security.md 2.x](https://raw.githubusercontent.com/appium/appium/2.x/packages/appium/docs/en/guides/security.md)).

## Cosmetic issues and unsupported claims are worth a quick pass

None of these blocks working automation, but an offline agent will repeat them. android.md line 10 says the options object sets `appium:automationName=UiAutomator2`. Client 6.1.5 actually sends `UIAutomator2`, which the server matches case-insensitively, so this is harmless. android.md line 197 names `com.google.android.permissioncontroller` while its example uses the `com.android.permissioncontroller:id/` prefix. Both are correct: the GMS package name differs, but the resource-ids keep the AOSP prefix ([source.android.com](https://source.android.com/docs/core/ota/modular-system/permissioncontroller?hl=en)). Saying so in one sentence avoids confusion. troubleshooting.md line 40 should mention that `appium driver run uiautomator2 reset` also uninstalls `io.appium.settings` (`scripts/reset.js`). android.md line 98's "Google plans to deprecate UiSelector" has no source and should be deleted. troubleshooting.md line 67's `ClassCastException` symptom is unsourced, although the `enforceXPath1` fix itself is documented. windows.md lines 83, 98 and 205 omit WPF's middle precedence step: AutomationId comes from `AutomationProperties.AutomationId`, then `x:Uid`, then `x:Name` ([FrameworkElementAutomationPeer.cs](https://raw.githubusercontent.com/dotnet/wpf/main/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Automation/Peers/FrameworkElementAutomationPeer.cs)).

The template also has small robustness gaps. `core/waits.py` uses `timeout or self._timeout`, which turns `timeout=0` into 15 s; it should be `self._timeout if timeout is None else timeout`. `pages/base_page.py` `is_displayed` can raise `StaleElementReferenceException`; wrapping it in try/except and returning False fixes that. The Calculator result regex keeps `1,234` grouping commas and truncates locales that use a space separator; adding `.replace(",", "")` and documenting it is enough. `pytest.ini`'s `log_file` resolves against the cwd, so the README should say "run pytest from the project root". shared-patterns.md line 161 promises a `ValueError` "naming the variable", but `_int()` raises a bare `int()` error; either soften the wording or wrap the conversion. Finally, the driver README says the host must be "Windows 10" and does not list Windows 11. The skill's "Windows 10/11" works in practice but is unofficial.

## Items that only a real Windows PC or device can settle

The audit ran on a Linux sandbox without PowerShell, Windows, an emulator or a phone. The following items therefore remain open.

**PowerShell argument handling.** Whether the unquoted comma list in B3 is actually split by `appium.ps1`, and whether the error is loud or silent.

**WinAppDriver install and versions.** Whether `install-wad` fails from a non-elevated terminal. Whether GitHub marks v1.2.99 as pre-release, which decides what a bare `install-wad` installs; tags `v1.2.1` and `v1.2.99` point to the same commit.

**Installers and Node.** Whether the winget ids `OpenJS.NodeJS.LTS` and `OpenJS.NodeJS.22` exist, and whether Appium 2.19 runs on Node 24 or 26.

**Calculator behaviour.** That the Store Calculator build on the target PC still has the `main`-branch AutomationIds. That the template's mode-switch fix works. Whether negative results carry invisible Unicode direction marks in the Name.

**Android device behaviour.** OEM permission-dialog ids (One UI, HyperOS). Whether Xiaomi's "USB debugging (Security settings)" needs a SIM or Mi account. The ApiDemos Views rows' content-desc on a live device. The `appWaitActivity` wildcard syntax. "UiAutomator2 4.x supports Android 5.0+".

**Unsourced messages and claims.** The WAD message "The system cannot find the file specified" for a bad AUMID. The .NET Framework (not .NET) WinForms AutomationId mapping. Compose `testTagsAsResourceId` behaviour. Whether driver ≥3.0.0 really stopped auto-installing WAD; this is consistent with the `install-wad` script but not checked against a changelog.

**Windows 11 builds.** Behaviour on 24H2/25H2 in general, since neither WAD nor the driver lists Windows 11 officially.

## Conclusion

The skill's knowledge of the Appium API is correct. Its weak spots are environmental: shell quoting, Node release timing, upstream driver majors that `driver update` now pushes toward, and Calculator's remembered state. Those are exactly the areas that drift after a skill is written, and they are the ones an offline agent cannot re-check. Two lessons follow for maintaining it. First, troubleshooting tables should quote strings copied from driver source, not paraphrases, because an agent's main debugging move is to search the logs for them. Second, any instruction that touches a version manager (`winget …LTS`, `driver update`, `install-wad` "latest") should name an exact version, because "latest" silently changed under this skill between authoring and November 2026. Apply B1–B4 and M1–M8 first. Together they remove every point where the agent's first attempt would fail or its log search would come up empty.
